Contexto del Proyecto

Distribuidora peruana de bebidas — datos reales del ERP web admin.casamarket.la

La Empresa

CasaMarket distribuye bebidas en Perú: Pepsi, Escocesa, Pilsen Callao. Más de 1,106 clientes, 62 productos y 6 vendedores activos.

Fuente de datos

El ERP admin.casamarket.la genera reportes .xlsx de ventas diarias. Se descargan automáticamente vía API REST con autenticación JWT.

El Problema

  • Sin visibilidad en tiempo real de ventas
  • Sin alertas ante anomalías del sistema
  • Sin proyecciones futuras de demanda
  • Historial disperso en Excel manuales

La Solución

Pipeline Kappa de streaming que procesa cada venta en < 30 segundos y la visualiza en dashboards en vivo con predicciones ML para todo 2026.

Apache Kafka — El Corazón del Pipeline

Message broker distribuido que desacopla productores de consumidores

¿Qué es Kafka?

Cola de mensajes distribuida y persistente. Los productores publican mensajes sin saber quién consume. Los mensajes sobreviven reinicios — el log es la fuente de verdad.

KRaft — Sin ZooKeeper

Kafka 3.7 usa su propio protocolo Raft para consenso del clúster. Elimina la dependencia de ZooKeeper → menor latencia y menos componentes.

Checkpoint — At-least-once

Spark guarda el offset de Kafka en disco (checkpoints). Si el job cae y se reinicia, retoma desde el último offset procesado sin perder ni duplicar datos en Parquet/PostgreSQL.

Prometheus — Observabilidad del Sistema

Monitorea la infraestructura cada 15 segundos — no toca los datos de negocio

¿Qué hace Prometheus?

Base de datos de series de tiempo que hace scraping (polling HTTP) a endpoints de métricas cada N segundos y las almacena en su TSDB local. Diseñado para monitorear infraestructura, no procesar datos.

Machine Learning — Predicciones 2026

LinearRegression por producto · 15 productos · 12 meses · 180 predicciones en PostgreSQL

¿Cómo funciona el modelo?

  1. Lee ventas desde PostgreSQL agrupadas por mes+producto
  2. Selecciona el Top 15 productos por ingresos
  3. Por cada producto entrena un LinearRegression
  4. Variable X = número de mes ordinal
  5. Proyecta enero–diciembre 2026
  6. Guarda 180 filas en predicciones_2026

Fórmula

y = β₀ + β₁ · mes_ordinal X = número de mes relativo al mínimo y = ingresos del mes β₀= intercepto (ingresos base) β₁= tendencia mensual (crecimiento)

Flujo de Datos — Paso a Paso

Desde el archivo Excel hasta Grafana, explicado tal como sucede

1

producer.py detecta documento nuevo

Cada 5 min consulta la API del ERP con token JWT. Si hay reporte nuevo, publica evento JSON en casamarket.documento.detectado.

2

consumer_downloader.py descarga el Excel

Escucha documento.detectado, descarga el .xlsx autenticado a la carpeta output/descargas/.

3

consumer_excel_parser.py parsea fila por fila

Escanea la carpeta cada 60s, lee el Excel con pandas, normaliza columnas y publica 1 mensaje JSON por fila en ventas.raw. Un Excel de 3,811 filas → 3,811 mensajes Kafka.

4

Kafka persiste los mensajes con offset

Los mensajes quedan en el topic con su número de offset. Son durables: si Spark no está listo, los mensajes esperan hasta que alguien los lea.

5

Spark lee el micro-batch cada 30 segundos

job_ventas.py lee todos los mensajes nuevos desde el último checkpoint, deserializa JSON, castea tipos y genera un DataFrame en memoria.

6

Spark escribe en paralelo a Parquet y PostgreSQL

Query 1 escribe Parquet (respaldo columnar). Query 2 usa foreachBatch → JDBC append → tabla ventas en PostgreSQL. Ambas en el mismo trigger de 30s.

7

Grafana refresca los dashboards cada 15s

Ejecuta queries SQL contra PostgreSQL y PromQL contra Prometheus. Los paneles se actualizan automáticamente — visibilidad total en menos de 1 minuto desde la venta.

Conceptos Teóricos Aplicados

Fundamentos de Big Data, streaming y arquitecturas modernas usados en el proyecto

Arquitectura Kappa

A diferencia de Lambda (batch + streaming), Kappa usa solo streaming como fuente de verdad. Todo el histórico vive en Kafka y se puede recomputar.

Streaming vs Batch

Batch: datos acumulados, procesa una vez al día. Streaming: cada evento en tiempo real. Spark usa micro-batches de 30s como punto medio.

Pub/Sub y Event Sourcing

Productores publican sin saber quién consume. El log de Kafka es la fuente de verdad histórica — los eventos son inmutables y reproducibles.

Windowing — Ventanas

Spark agrupa eventos en ventanas de 5 minutos con watermark de 10 min. El watermark tolera mensajes tardíos sin afectar resultados ya emitidos.

At-least-once Delivery

Kafka + Spark garantizan que cada mensaje se procesa al menos una vez. Los checkpoints guardan el offset procesado — ante una caída, reanuda desde ahí.

Parquet — Formato Columnar

Agrupa valores de la misma columna en disco. Un SELECT SUM(total) solo lee la columna total, no el registro completo → 10× más rápido para analítica.
